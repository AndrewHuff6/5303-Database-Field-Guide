# MongoDB — Concept Map Answers

MongoDB's column of the [concept map](../../reference/concept_map.md), with
the detail that doesn't fit in a table cell. Same questions, same order, for
every engine.

| Question                   | MongoDB                                                                                                                                                        |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Process model**          | Client-server. The server process is `mongod`; clients connect over the network and send commands (`find`, `aggregate`, `insert`), not SQL text.               |
| **Top-level container**    | A **deployment**: one `mongod`, a replica set (copies of the same data), or a sharded cluster.                                                                  |
| **Namespace inside it**    | Database → **collection**. Both are created the first time something is written to them; there's no `CREATE TABLE`.                                           |
| **Unit of data**           | The **document**: BSON (binary JSON) with typed fields, nested documents, and arrays. Up to 16 MB each. Every document has a unique `_id`.                    |
| **Who are the users?**     | Users stored in an authentication database (usually `admin`), with roles. Authentication is **off** unless you turn it on (this unit's container leaves it off). |
| **Permission granularity** | Built-in and custom roles grant actions (`find`, `insert`, ...) on a database or a collection. No row-level rules; views can hide fields.                      |
| **Schema enforcement**     | **None by default**: any document shape is accepted. An optional `$jsonSchema` **validator** per collection checks types and required fields.                 |
| **Relationships**          | Embed the related data, or store a reference (an id) and follow it with `$lookup`. **References are never enforced**, not even by a validator.                |
| **Index types**            | Single-field, compound, multikey (indexes every element of an array), text, 2dsphere (geography), hashed, wildcard, TTL (documents that expire).              |
| **How to see the plan**    | `explain("executionStats")`: the winning plan's stages, the rejected plans, and keys examined / documents examined / documents returned.                      |
| **Transactions**           | A write to one document is always atomic. **Multi-document transactions** exist but require a replica set; conflicting transactions abort and must be retried. |
| **Unit of locking**        | The **document**. Plain writes to the same document take turns; transactions that conflict on one fail with a write conflict.                                  |
| **Code inside the DB**     | No stored procedures or triggers in the server. Aggregation pipelines run server-side; change streams let outside code react to writes.                      |
| **Durability knob**        | **Write concern**: `w` (how many replica-set members must have it) and `j` (wait for the on-disk journal). The default is `w: "majority"`.                  |
| **Replication model**      | **Replica sets**: one primary takes writes, secondaries copy its oplog. If the primary fails, the members elect a new one automatically.                      |
| **Sharding model**         | **Sharded clusters**: a collection is split across shards by a **shard key**; routers (`mongos`) send each query to the shards that hold its data.           |
| **Backup**                 | `mongodump` / `mongorestore` (data, indexes, collection options), or file-system snapshots of a member.                                                       |
| **CLI**                    | `mongosh`                                                                                                                                                       |
| **Python driver**          | `pymongo`                                                                                                                                                       |

## Notes

- **No auto-increment.** `_id` defaults to an `ObjectId` (12 bytes: a
  timestamp, a random value, a counter), generated by the driver without
  asking the server. Numeric ids, as `store` uses, need a counter document
  that every writer increments ([§8](08_concurrency/)).
- **"Schema-less" means the schema lives in your code.** The documents
  still have a shape; MongoDB just doesn't check it unless you add a
  validator. [§4](04_model/) shows what a validator can and can't catch.
- **Joins are a design smell, not a feature gap.** `$lookup` works, but a
  design that needs it on every read was probably modeled like SQL. §4 Part
  B measures the difference.
