# 04 — Model the data: PostgreSQL

> **Fixed question:** How does the `store` dataset *want* to look in this engine?
>
> **Student artifact:** Your `roles.sql` and the checks that prove it (see
> [Part B](#part-b--your-turn-who-may-touch-what))

PostgreSQL is relational, so the eight tables from
[SQLite §4](../../01_sqlite/04_model/) don't change: the facts are the same
facts. What changes is **how much the engine enforces** and **who is allowed
to touch what**. SQLite and DuckDB had no answer to the second question,
since anyone who could read the file could read everything. A server does.

- **Part A** is a worked example: the `store` schema in PostgreSQL, and the
  namespaces it lives in.
- **Part B** is your turn: design the permissions for three kinds of user,
  and prove they work.

## Part A — Walkthrough: the `store` schema in PostgreSQL

Build the classroom copy first ([§5](../05_load/)), then follow along in
`psql` with `SET search_path TO classroom;`.

### A1. Types that mean something

Open [schema.sql](schema.sql) next to
[SQLite's](../../01_sqlite/04_model/schema.sql).

| Column | SQLite | PostgreSQL | What it buys you |
| ------ | ------ | ---------- | ---------------- |
| `purchase_date` | `TEXT` + a `GLOB` check | `date` | Real date arithmetic; a malformed date can't get in |
| `amount`, `unit_price` | `NUMERIC` (stored as a float) | `numeric(10,2)` | Exact cents |
| names, codes | `TEXT` | `text` | The same; `varchar(n)` would only add a length limit |
| `purchase_id` | `INTEGER PRIMARY KEY` (the rowid) | `integer GENERATED BY DEFAULT AS IDENTITY` | New ids from a counter you can see and move |

> **Predict:** SQLite stored `'abc'` in an `INTEGER` column without
> complaint. What does PostgreSQL do with
> `INSERT INTO products VALUES (9999, 'Test', 'abc');`?

<details>
<summary>Answer</summary>

```
ERROR:  invalid input syntax for type numeric: "abc"
```

A declared type is a rule here, not a preference. That's the "strict" in
the concept map's *Schema enforcement* row.

</details>

### A2. Constraints that are always on

| Constraint | SQLite | PostgreSQL |
| ---------- | ------ | ---------- |
| `NOT NULL`, `CHECK`, `UNIQUE`, `PRIMARY KEY` | enforced | enforced |
| `FOREIGN KEY` | **off** unless `PRAGMA foreign_keys = ON`, per connection | **always on** |
| `ON DELETE CASCADE` | works when foreign keys are on | works |
| Index on a foreign-key column | not created for you | **not created for you either** |

That last row surprises people. PostgreSQL checks every foreign key, but it
doesn't index the column that holds it. Deleting a customer has to find
their purchases, and without `idx_purchases_customer` that's a scan of the
whole `purchases` table. [indexes.sql](../05_load/indexes.sql) adds those
indexes for the `idx_*` schemas; `noidx_*` goes without, and §7 measures the
difference.

> **Predict:** `cards.customer_id` says `ON DELETE CASCADE`;
> `purchases.customer_id` says `ON DELETE RESTRICT`. What happens to
> `DELETE FROM customers WHERE customer_id = 1;` in the classroom schema?

<details>
<summary>Answer</summary>

```
ERROR:  update or delete on table "customers" violates RESTRICT setting of foreign key
        constraint "purchases_customer_id_fkey" on table "purchases"
DETAIL:  Key (customer_id)=(1) is referenced from table "purchases".
```

Customer 1 has a purchase, and `RESTRICT` protects it. If they had no
purchases, the delete would succeed and **take their cards with it**
(`CASCADE`). The schema encodes a business rule: you can forget a customer
who never bought anything, never one with a purchase history.

</details>

### A3. Where the tables live: database → schema → table

SQLite kept each experiment database in its own file. PostgreSQL keeps all
of them in **one database**, `course`, as **schemas**: named folders of
tables.

```
course                     (a database)
├── classroom              (a schema: 1,000 purchases from the CSV)
├── idx_10k   noidx_10k    (schemas: the generated data, with and without indexes)
├── idx_100k  noidx_100k
├── idx_1m    noidx_1m
└── writes                 (a scratch copy for 08_concurrency)
```

Every schema has its own `purchases`, `customers`, and so on.
`SET search_path TO idx_1m` chooses which one an unqualified name means;
`idx_1m.purchases` names one explicitly. That's how the API's `?db=noidx_1m`
works here: same tables, different schema.

> **Predict:** with `SET search_path TO idx_10k, classroom`, how many rows
> does `SELECT count(*) FROM purchases` return?

<details>
<summary>Answer</summary>

10,000. The path is searched in order and the first match wins:
`idx_10k.purchases` exists, so `classroom.purchases` is never considered.
A name that exists only in `classroom` would still be found there.

</details>

## Part B — Your turn: who may touch what

In SQLite, "permissions" meant file permissions. Here, the server checks
every statement against the role that sent it. Read
[Users, roles, and schemas](../../../reference/topics/users_roles_schemas.md)
first: it explains roles, `GRANT`, and the three levels of permission
(database, schema, table).

### B1. The brief

The `classroom` schema needs three kinds of access:

| Role | Who | May | Must not |
| ---- | --- | --- | -------- |
| `store_api` | the measurement API | read every table; **insert** purchases | change or delete anything; touch other schemas |
| `store_analyst` | a person writing reports | read every table and the `purchase_details` view | write anything at all |
| `store_readers` | nobody logs in as this | — | — |

`store_readers` is a **group role**: give it the permissions both of the
others need, then make them members, so the shared part is written once.

### B2. Predict, then write `roles.sql`

Before writing anything, fill in the middle column: which privilege, on
which object, makes each statement succeed? Then write `roles.sql` so that
every row of the table below behaves as listed.

`student` is a superuser in the Docker container, so you can create roles.
Test each one with `SET ROLE`, which makes your session act as that role
until `RESET ROLE`:

```sql
\i roles.sql
SET ROLE store_analyst;
SELECT count(*) FROM classroom.purchase_details;     -- check 1
RESET ROLE;
```

| # | As | Statement | Must |
| - | -- | --------- | ---- |
| 1 | `store_analyst` | `SELECT count(*) FROM classroom.purchase_details` | succeed |
| 2 | `store_analyst` | an `INSERT` into `classroom.purchases` | fail |
| 3 | `store_api` | an `INSERT` into `classroom.purchases` | succeed |
| 4 | `store_api` | `UPDATE classroom.products SET unit_price = 0` | fail |
| 5 | `store_api` | `DELETE FROM classroom.purchases WHERE purchase_id = 1` | fail |
| 6 | `store_api` | `SELECT count(*) FROM idx_10k.purchases` | fail |
| 7 | either | `SELECT count(*) FROM classroom.customers` | succeed |
